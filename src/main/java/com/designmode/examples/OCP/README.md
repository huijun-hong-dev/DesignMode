# 开闭原则（OCP — Open-Closed Principle）

> **Software entities should be open for extension, but closed for modification.**
>
> 软件实体应当对扩展开放，对修改关闭。

翻译过来：**加新功能的时候，只加新代码，不改老代码。**

**问题：** 每次加新支付方式，`OrderService` 都得改。改老代码意味着：
- 可能引入新 bug
- 需要重新测试老功能
- 多人协作时容易冲突

---

## 二、怎么做到"不改老代码就能加功能"

核心手段：**面向接口编程 + 多态**

---

## 三、OCP 的实现手段

| 手段 | 怎么帮到 OCP |
|------|-------------|
| 接口/抽象类 | 定义稳定的契约，具体实现可以随便加 |
| 多态 | 客户端依赖接口，运行时注入不同实现 |
| 设计模式 | 工厂、策略、装饰器等都是在帮你遵守 OCP |
| 配置驱动 | 从配置文件/数据库读类型映射，连工厂都不用改 |

---


## 四、你已经学过的东西跟 OCP 的关系

### 4.1 简单工厂 vs OCP

| | 简单工厂 | 工厂方法 |
|--|---------|---------|
| 加新产品 | 改工厂的 switch | **加新工厂类，不改老代码** ✅ |
| OCP 遵守程度 | 部分（集中了但还是改） | 完全 |
策略模式天然符合 OCP——算法随便加，上下文不动。

### 4.3 SRP vs OCP 的关系

- **SRP** 说：一个类只干一件事 → 拆开
- **OCP** 说：拆开之后，加功能别改老代码 → 用接口

SRP 是 OCP 的前提。不拆开，一个类啥都干，加啥功能都得改它。

---

## 五、违反 OCP 的信号

| 信号 | 说明 |
|------|------|
| 加功能时 `if-else` 又多一个分支 | 类型判断散落多处 |
| 改一个类要通读全文怕影响别的 | 职责没拆干净 |
| 每次发版要回归测试一堆老功能 | 老代码被动了 |
| 同事说"我不敢动那个类" | 改不动了 |

---

## 六、容易踩的坑

### ❌ 过度设计：为了 OCP 把什么都抽象
一个接口一个实现，永远不变 → **别抽象**，直接写类。OCP 是"可能变的地方才留扩展口"，不是"所有地方都留口"。

### ❌ 预测了错误的变化方向

你猜以后会加新支付方式 → 抽象了 Payment → 后来需求变了（要加退款、对账）→ 抽象方向猜错了，白忙。

> **原则：等到第二次变化时再抽象，别第一次就搞。** 这就是"Rule of Three"——同样的变化出现第三次时再重构。

---

## 七、现实类比

> 你开了一家餐厅。菜单是接口（稳定），菜品是具体实现。加新菜只需要在菜单上加一行、后厨出新菜，不用把厨房拆了重建。但如果菜单写死在墙上不能改（没留扩展口），每加一道菜得重新装修——这就是违反 OCP。

---

## 八、跟其他 SOLID 原则的关系

| 原则 | 跟 OCP 的关系 |
|------|-------------|
| SRP | 拆得干净，OCP 才好做（基础） |
| OCP | 拆开后通过接口扩展（目标） |
| LSP | 子类能替换父类，OCP 的多态才成立（保障） |
| ISP | 接口够小够专，扩展时才不会被迫实现不需要的方法 |
| DIP | 依赖抽象不依赖具体，OCP 才能"对修改关闭" |

> OCP 是 SOLID 的核心目标，其他原则都是在帮它落地。

---

## 九、一句话总结

> **OCP = 加功能只加新文件，不改老文件。做到这一点靠面向接口 + 多态 + 设计模式。**
